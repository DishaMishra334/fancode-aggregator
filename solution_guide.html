1. Setup & Execution Guide

The service is completely self-contained. A reviewer can launch and test the entire aggregator, both mock providers, the persistent database, and the interactive Swagger UI using either Docker or the Maven wrapper.

Option A: Docker-Based Setup (Preferred & Recommended)

Uses a multi-stage Docker build with Eclipse Temurin Java 21 Alpine JRE. Requires zero Java or Maven installation on the host machine. 

# 1. Navigate to the project directory:
cd C:\Users\Deepak\OneDrive\Desktop\fancode-aggregator

# 2. Build image and start the container:
docker compose up --build

# (Optional: Run in background mode)
docker compose up -d --build
Container Specifications:
  • Exposes HTTP port 8080 on http://localhost:8080.
  • Mounts host directory ./data to /app/data for durable, crash-proof H2 persistence.
  • Includes container health checks querying wget -qO- http://localhost:8080/matches.
# To stop and remove the container:
docker compose down

Option B: Native Local Setup via Maven Wrapper

If running natively on a host machine with Java 21 installed, use the included Maven wrapper without installing Maven: 

# On Windows (PowerShell / Command Prompt):
.\mvnw.cmd clean spring-boot:run

# On Linux / macOS:
./mvnw clean spring-boot:run

4. Assumptions & Key Design Decisions

Assumptions Documented

  1. Cricket Engine Scope: The service does not calculate runs, wickets, or overs by interpreting commentary text. Score snapshots (runs/wickets, overs) are authoritative facts emitted by providers and stored as-is.
  2. Provider Numbering Independence: Provider A and Provider B number sequences independently. Those numbers are never comparable across providers.
  3. Ball Identity Stability: Each ball has a stable ballId (e.g. inn1-12.4). Corrections retain the same ballId with an incremented revision counter.
  4. Single-Process Durability: A single local process backed by an embedded file-based relational database constitutes a complete solution. Stored data survives JVM restarts and system reboots.
  5. Provider Failure Tolerance: Temporary provider outages (such as HTTP 503 from Provider B) leave the last good stored match available to clients without data loss or exceptions.

Key Architectural Design Decisions

1. Embedded File-Based Database (H2)

Configured at jdbc:h2:file:./data/fancodedb;DB_CLOSE_DELAY=-1. Zero installation overhead for reviewers while guaranteeing ACID transactions and persistence across restarts.

2. Two-Tier Idempotency Model

Push: Fast-path uniqueness on (provider, delivery_id) returning duplicate_ignored.
Poll: Entity-level checks on (sequence, revision).

3. Lexicographical Monotonicity

Snapshot candidate (s2, r2) is strictly newer than stored (s1, r1) iff:
(s2 > s1) || (s2 == s1 && r2 > r1).
Older or identical snapshots are safely rejected.

4. Sequence-Gap Tolerant Commentary

Scores update immediately; commentary does not block scores. Client commentary is sorted by sequence ASC. Late balls automatically slot into position.

5. Deterministic Precedence

Configured primary provider (provider-a) is served first. If primary data is absent, secondary (provider-b) is served. Sequences are never compared across providers.

6. Zero-Setup Docker & Swagger

SpringDoc OpenAPI 3.0 provides an interactive web UI at /swagger-ui/index.html. Multi-stage Docker build ensures execution on any OS with one command.

Webhook Response Contract & Crash Recovery Protocol

HTTP Status Response Body Meaning Provider Action
200 OK {"status": "accepted", "deliveryId": "..."} Event committed to persistent database. None (Acknowledged).
200 OK {"status": "duplicate_ignored", "deliveryId": "..."} DeliveryId was previously processed. State unchanged. None (Acknowledged).
400 Bad Request {"error": "...", "status": 400} Malformed payload (missing provider or deliveryId). Fix payload; do not retry as-is.
500 Error {"error": "...", "status": 500} Database crash or unhandled error before commit. Retry delivery with the exact same deliveryId.
